# Karpathy 式编码智能体准则

## 摘要

这篇笔记整理自 `andrej-karpathy-skills` 的 README。原文把 LLM 编码中常见的问题归纳为四类：替用户做未经验证的假设、把简单问题复杂化、顺手修改无关代码，以及缺少可验证的成功标准。

对应的改进方向也很直接：编码前先澄清，默认选择简单方案，只改任务真正需要的部分，并把“完成任务”转化为可以运行、可以检查、可以复现的目标。

这组准则适合作为 Codex、Claude Code 等编码智能体的轻量行为规范。它和 [[智能体优先工程实践]] 是互补关系：后者偏向工程系统如何支持智能体，本文偏向智能体在日常编码时应该如何行动。

## 核心原则

### 先想清楚，再写代码

智能体不应该在含糊任务里偷偷选择一种解释然后一路写下去。遇到歧义时，应先说明自己的假设，列出可能的理解；如果误判成本较高，就向用户确认；如果有更简单或更稳妥的做法，也应主动提出。

这条原则要解决的是“自信地跑偏”：模型看起来执行力很强，但其实前提没有被验证。

### 简单优先

优先写能解决当前问题的最少代码。不要为了未来可能的需求添加抽象、配置项、扩展点或复杂错误处理。

一个实用判断是：如果资深工程师看到这段实现会觉得“这事没必要这么复杂”，那就应该收回去简化。一次性逻辑不必抽象，明确边界内不会发生的情况也不必层层防御。

### 外科手术式修改

修改范围应该和用户请求直接对应。匹配现有风格，只碰必须修改的代码；不要顺手重构旁边的模块、重排无关格式、改写自己没有理解透的注释，或者删除早就存在的“看起来没用”的代码。

如果当前改动制造了新的未使用 import、变量或辅助函数，应当清掉；但不要借机清理历史遗留问题。发现无关问题时，可以在汇报里说明，而不是把它混进本次 diff。

### 用目标驱动执行

把“修一下 bug”“加个校验”“重构这里”这类命令，转换成可验证目标。例如先写出能复现 bug 的测试或命令，再让它通过；先定义无效输入应该怎样失败，再补实现；重构前后都跑同一组测试。

多步骤任务可以维护一个很短的计划，每一步都带上验证方式。好的成功标准能让智能体自己闭环；模糊的“让它能用”通常会导致反复猜测。

## 使用方式

- 把这些原则放在项目规则之后，作为编码智能体的补充行为规范。
- 开始复杂任务前，先明确假设、歧义、取舍和验证方式。
- 实现时优先选择符合现有代码风格的最小方案。
- 控制 diff，只保留和本次目标直接相关的改动。
- 将“修复、添加、重构”翻译成测试、构建、复现命令、截图或其他可检查结果。
- 做代码审查时，可用这四条检查是否存在过度设计、隐藏假设、顺手重构或无法验证的完成声明。

## 适用边界

原始剪藏中有少量编码损坏字符，但英文主体内容可读。本文是基于本地 raw 笔记和链接 README 的中文综合整理，不是原文逐字翻译。

这些准则是编码智能体的行为启发，不应覆盖更高优先级的项目规则、用户当轮指令、安全要求、发布流程或团队约定。对明显的一行小改，不需要机械执行完整流程；对含糊、复杂或影响面大的任务，则应更严格地应用。
