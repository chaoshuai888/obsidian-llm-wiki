# 智能体优先工程实践

## Summary

在智能体优先的软件工程中，人类工程师的主要工作从直接写代码转向设计环境、表达意图、建立约束和维护反馈回路。Codex 负责执行实现、测试、修复、评审响应和工具化操作；人类负责决定目标、验收标准、系统边界，以及什么样的结果才算清晰、可靠、可维护。

这篇原始材料来自 OpenAI 2026-05-05 发布的工程文章，描述了一个由 Codex 生成约百万行代码、经历真实交付和用户使用的内部产品实验。其核心经验不是“让模型随意生成更多代码”，而是把仓库、工具、文档、测试、可观测性和评审流程建设成智能体可读取、可验证、可修改的环境。

## Key Lessons

`AGENTS.md` 应当作为地图，而不是百科全书。长篇全量指令会挤占上下文、快速过期且难以机械验证；更可靠的结构是短入口文件指向结构化 `docs/`、架构说明、执行计划、质量规则和领域文档。

知识必须进入智能体能访问的记录系统。存放在聊天、会议、个人记忆或外部文档中的信息，如果没有以本地 Markdown、代码、脚本、测试或配置的形式进入仓库或 wiki，对下一次智能体运行来说基本等同于不存在。

智能体需要反馈回路，而不只是任务描述。可驱动的 UI、日志、指标、追踪、截图、DOM 快照、测试命令和结构化错误信息，会让 Codex 能够复现问题、验证修复并反复迭代。

架构边界要可强制执行。文章强调用自定义 linter、结构测试、分层依赖规则、文件大小限制、命名约定和平台可靠性要求来固化不变量。对智能体来说，明确且可验证的边界比口头偏好更有效。

代码库应为智能体可读性优化。可读性不仅面向人类新成员，也面向未来的智能体运行；本地、版本化、可交叉链接、可执行的材料比散落在外部系统中的知识更有价值。

人类品味应被编码进系统。评审意见、重构原则、用户反馈和缺陷复盘若反复出现，应沉淀成文档、检查器、测试或工具，而不是依赖人类每次重新提醒。

## How To Use

在 Codex/Claude Code 工作流中，可把这篇材料转化为以下操作习惯：

- 保持入口指令短而稳定，用它导航到权威文档。
- 对复杂任务先创建或读取执行计划，把进度和决策留在本地文件中。
- 为智能体提供可运行的验证命令和可观察信号，而不是只要求“检查一下”。
- 当智能体失败时，把失败视为系统缺少工具、约束、文档或反馈的信号。
- 将重复性的人工评审意见转换为自动检查或明确规范。
- 对个人 LLM Wiki，同样遵循 raw -> review -> draft/wiki 的流程；本地 `olw` 模型不可用时，可由当前 Codex 或 Claude Code 会话生成待审核草稿，但不要直接发布为正式 wiki。

## Boundary

这篇材料来自 OpenAI 内部产品实验，适合提炼智能体优先工程的原则，但不应机械套用其吞吐量、团队规模或完全不手写代码的做法。是否能复现类似效果，取决于仓库结构、测试覆盖、工具链、可观测性、文档质量和团队接受的风险边界。
